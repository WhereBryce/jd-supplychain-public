JD SUPPLY CHAIN · KNOWLEDGE SYSTEM

知识不是被存放，
而是在循环中生长。

大家把手里的文件、经验和问题放进来，AI 帮忙整理，团队负责确认。 最后，这些零散内容会变成找得到、看得懂、还能直接支持日常工具和自动化应用的团队知识。

01 / The Loop

一条知识如何完成旅程

不用一开始就整理得很完美。先把东西放进来，再一步步说明“这是什么、从哪里来、跟什么有关、能拿来做什么”。

STEP 01

捕获碎片

文字、链接、图片、Word、PPT、PDF、Excel 或半成品想法，直接投入 Inbox。

简单说：先收进来，别让知识只留在聊天记录和个人电脑里。
STEP 02

原子化

把材料拆成一个概念或一个事实一篇的自足笔记，并保留来源。

简单说：一张纸只讲清一件事，以后更容易找到和重复使用。
STEP 03

连接成网

补充 frontmatter、标签、双链，并挂入对应领域的 MOC 导航。

简单说：给它贴标签、放进目录，并注明它和哪些知识有关。
STEP 04

跨域合成

沿知识网络寻找矛盾、空白、类比和假设，形成候选洞察。

简单说：把不同笔记放在一起看，找出以前没注意到的规律。
STEP 05

验证回流

由人补充信息、校准置信度；结论再裂变为知识，回到领域体系。

简单说：请懂业务的人确认；确认后的结论再放回知识库。
↻ 开放问题会重新进入 Inbox，让知识库形成持续复利，而不是一次性归档。
02 / Architecture

六层结构，各司其职

可以把它理解成一个图书馆：收件台接收材料，书架保存知识，目录帮助找书，关系网串起内容，统一词典保证大家说的是同一件事。

_Inbox/

入口层

无门槛接收材料。一条碎片一个文件，降低 SharePoint 多人协作冲突。

像：图书馆的收件台。
atom · source

知识层

原子笔记承载可复用事实，来源笔记承载一份材料的提炼，并明确出处。

像：整理完成、可以借阅的书。
moc

导航层

总地图与领域地图提供阅读路径，并登记高复用的枢纽笔记。

MOC 是什么：就是某个主题的目录页。
[[双链]] · #标签

网络层

关联连接相邻知识；杠杆点、口径陷阱、类比等思维透镜连接跨域结构。

双链是什么：A 提到 B 时，B 也能知道 A 提过自己。
insight · synthesis

洞察层

把推理结果与有据事实分开，记录主张、依据、置信度和待验证问题。

为什么分开：避免把“我们的判断”误当成“已经确认的事实”。
class · ontology.yaml

本体层

标准化订单、SKU、库存、仓等实体及关系，为机器查询和应用提供统一口径。

本体是什么：一份全团队和所有 App 共用的业务词典。
03 / Collaboration

团队成员如何贡献知识

贡献知识不等于写论文。团队成员只需要把知道的东西交出来，并在需要时回答问题；整理工作交给 AI 和轮值管家。

1

提交：先贡献，不要求先整理

把文件或想法放进“收集箱” _Inbox/。一条内容建一个新文件，避免大家同时改同一份文档。

例如：库存日报、会议结论、仓网截图、一个尚未验证的业务判断。
2

保留：记录是谁贡献、从哪里来

整理时记下“谁提供的”与“原材料在哪里”，这样有疑问时能找到知情人，也能回看原文。

结果：团队共享知识，但不丢失知识背后的责任人与上下文。
3

整理：AI 拆解，管家审核

AI 把长材料拆成一件事一篇，或者补进已有笔记；同时加上摘要、分类、来源和相关知识。

怎么分：确认过的事实进“知识卡片”，整份材料的摘要进“来源笔记”，新想法进“洞察笔记”。
4

连接：挂到团队共同地图

把笔记放进相应主题目录，并标出它与哪些内容有关，让别人能顺着关系继续阅读。

效果：个人经验从“某人知道”变成“团队可发现、可组合”。
5

反馈：使用者继续纠正和补全

以后发现新数据、App 报错或业务规则变化，就回来修正旧内容，或者补一张新的知识卡片。

闭环：贡献不是一次性交稿，而是共同维护一个持续生长的事实网络。
✓ 新文件协作，减少 SharePoint 冲突
✓ 来源与贡献者保留，可追溯
✓ 每周 steward 轮值清理 Inbox
04 / Human + AI

人做判断，AI 做放大

AI 不是事实来源，也不替代业务确认。它负责降低整理成本、发现连接和暴露问题；人负责输入经验与最终判断。

团队成员

  • 贡献资料、业务经验和实际数据
  • 确认重要洞察是否值得沉淀
  • 回答开放问题并校准置信度
  • 由轮值管家定期清理 Inbox

AI 助手

  • 提炼、拆分并按统一模板结构化
  • 补充双链、标签和 MOC 入口
  • 跨域扫描矛盾、空白与同构关系
  • 保留来源，不确定处不擅自编造
05 / Ontology Evolution

本体如何随业务迭代

这份“统一业务词典”不会一次写完。只有当新资料或新 App 真的需要时，团队才补充词条、字段和关系，并通知所有使用它的 App。

01 · SIGNAL

发现语义缺口

新资料、团队问答或 App 开发发现缺少实体、字段或关系。

例如：补货 App 需要“预测日销”，但词典里还没有。
02 · DEFINE

对齐业务口径

确认名称、定义、属性边界、所属子域，以及与现有实体的关系。

先问清：怎么算、单位是什么、谁负责、与库存是什么关系。
03 · UPDATE

同步两种表示

更新 Classes 类笔记与 ontology.yaml；新关系须先进入谓词白名单。

两份都改：一份给人看，一份给程序读。
04 · VERSION

提升版本

修改 version 与 updated，使依赖应用能够感知本体已经变化。

作用：像软件升级号，提醒 App“公共规则变了”。
05 · ADOPT

应用更新契约

应用同步新本体，更新 data-contract，并通过字段与版本校验。

不通过就停：宁可明确报错，也不按错误口径继续运行。

实例：补货应用提出新需求

当智能补货需要“预测日销”和“最终补货件数”，先把 Forecast 与 Replenishment 建成本体实体，再让应用消费。不能只在某个脚本里私自创造口径。

forecast
  depends_on → inventory

replenishment
  depends_on → forecast
  depends_on → inventory / quota / asn
  transforms_to → order

07 / Plain Glossary

页面里的词，到底什么意思

如果只记住这一组翻译，就足够理解整个知识库。

Inbox / 收集箱大家暂时把原材料放进来的地方。
Atom / 原子笔记只讲清楚一件事的知识卡片。
MOC / 内容地图一个主题的目录页和推荐阅读路线。
双链两篇笔记互相知道对方，方便顺藤摸瓜。
Insight / 洞察根据事实推出来、但仍可能需要验证的新判断。
Ontology / 本体人和 App 共用的标准业务词典。
Data Contract / 数据契约App 使用哪些数据、按什么口径算的书面约定。
SSOT / 单一事实源同一个定义只认一个官方出处，避免各说各话。
Steward / 轮值管家每周负责整理收集箱、确保知识进入正确位置的人。
